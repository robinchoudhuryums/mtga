CHANGES:
MATCH-PASTE TRANSPORT WASTE | scripts/parse_matches.py |
  Added `ingest_watermark()`, `filter_since()`, and three flags: `--since YYYY-MM-DD`,
  `--since-last`, `--watermark`.

  WHAT WAS NOT DONE, and it was the obvious fix: the extractor does NOT truncate or
  consume Player.log / arena.log. That archive is what makes re-ingest possible and what
  `--annotate` joins against by matchId AFTER the fact, so consuming it would permanently
  lose any match whose `--apply` failed or was never run. The waste is in the pipe, so the
  fix is in the pipe.

  THE WATERMARK IS DERIVED FROM matches.csv, never a sidecar stamp. The CSV already stores
  Date and Match ID; a second file recording the same fact is a second thing that can
  drift, which is this repo's recurring failure. There is nothing to keep in sync because
  there is nothing else.

  HAND ROWS ARE EXCLUDED from the watermark, and this is the load-bearing rule. A `--add`
  row (a phone game the desktop log never saw) has no matchId and a user-supplied date, so
  letting one advance the mark would silently filter LOG matches that were never ingested
  out of every future paste. The filter is only ever as confident as the log-derived rows.

  THE BOUNDARY DAY IS INCLUSIVE. A day routinely holds both ingested and un-ingested
  matches — this session's own paste did — so `> cutoff` would drop a real match whose
  neighbours happened to be recorded first. Keeping the day costs a handful of lines and
  hands the overlap to the matchId dedup, which is what dedup is for.

  ORDER IS PRESERVED AND NEVER SORTED. `resolve_matches` walks the log in order and pairs
  each result with the most recent `Match to <userId>` header — the only place the local
  seat appears — so re-ordering would mis-attribute every W/L. `filter_since` removes
  lines; it never moves one, and a test pins that.

  DATING RULES, one per line shape, each earned by what breaks otherwise:
   · EventSetDeckV3 by its OWN `LastPlayed` — it PRECEDES the matches it explains, so
     inheriting a neighbour's date misfiles it by a session and un-attributes every match
     in it.
   · a UnityCrossThreadLogger line by its own local timestamp.
   · anything else — notably the bare `{...finalMatchResult...}` blob, which has no date
     prefix — INHERITS the last dated line above it, i.e. the header it belongs to.
   · an undatable line before any date is known is KEPT. Dropping what cannot be dated is
     guessing in the destructive direction, and this is a convenience over a record that
     is already correct.

  `--watermark` prints the bare date on STDOUT and everything explanatory on STDERR, so a
  shell script can capture it: `d=$(parse_matches.py --watermark)`.

MATCH-PASTE TRANSPORT WASTE | .claude/commands/log-matches.md |
  `mtga-matches` now takes an optional `YYYY-MM-DD` and filters the CLIPBOARD with an awk
  state machine mirroring `filter_since` line for line. This half matters because the
  Arena machine has NO repo checkout (the skill's own documented common case), so a
  repo-side flag alone could not shrink the paste — it would only shrink what the parser
  reads after the whole block had already been carried into a session.
  VERIFIED byte-identical: the awk and Python filters produced the same 16 kept lines from
  the same 24-line real paste, diff-clean. The doc says to change both together, because
  two implementations of one question that can disagree is exactly the shape this repo
  keeps paying for.
  POSIX awk only (`match()` + RSTART/RLENGTH, no gawk third-arg `match`), because macOS
  ships BWK awk.

REGRESSION RISKS:
  - The three flags are OPT-IN and default off. With none passed, `filter_since` is never
    called and the parse path is byte-for-byte what it was.
  - `ingest_watermark` and `filter_since` are new functions with no prior callers.
  - No existing signature, return type or default changed.
  - The filter is applied ONCE, right after the source is read and before every consumer,
    so the whole log path (matches, `#: arena:` harvest, `--sync-names`, `--map-decks`)
    sees one consistently filtered text rather than each deciding for itself.
  - Old behaviour correct anywhere? Yes, in one direction, and it is preserved: pasting
    everything is still right and still free. The filter can only ever make a paste
    SMALLER than the correct answer if the watermark were wrong, which is why hand rows
    cannot advance it and why the boundary day is inclusive. When in doubt the documented
    advice is to drop the flag.
  - Residual: `filter_since` dates a line by the best evidence it carries. A log shape
    with neither a timestamp nor a `LastPlayed`, appearing before any dated line, is KEPT
    — deliberately, but it means the filter is a best-effort shrink, not a guarantee.
