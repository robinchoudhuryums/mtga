CHANGES:
GRANTED-KEYWORD TAG GAP | scripts/tag_synergies.py |
  Added `_GRANTED_KEYWORDS` (12 evergreen keywords), `_GRANT_RES` (one pattern each),
  two rejection filters, and `granted_keywords(text)`; wired a pass into `tags_for` that
  adds the keyword AND its implied themes through the SAME `KEYWORD_THEMES` table the
  native path uses, so the two cannot drift — that drift being the entire bug.
  SCOPING, all three earned rather than assumed:
   · Reminder text is stripped for this pass only. It is parenthetical and QUOTES the
     keyword it explains, so a raw scan would tag every card whose reminder names one.
   · An OPPONENT-facing grant is rejected — "creatures your opponents control gain haste"
     is a drawback, not a haste payoff — judged on the CLAUSE around the match, not the
     whole text, so an opponent clause elsewhere cannot suppress a real grant.
   · Negations ("loses flying", "can't have hexproof") are rejected.
  Order comes from iterating a TUPLE, so the output is a total order (G-54); verified by
  a byte-compare of `cuts`/`similar`/`suggest` under two PYTHONHASHSEED values.
  NOT filtered by `is_noise_keyword`: that filter exists for artifacts of Scryfall's
  keyword LIST (Jump on every jump-start card, K-01), and text reading "gains flying"
  is not that.

GRANTED-KEYWORD TAG GAP | scripts/check_patterns.py |
  Registered all 14 new patterns. The gate caught every one of them unregistered on the
  first run — 12 grant regexes nested in a dict (invisible to the completeness scan, the
  same shape that let `_TARGET_GATES` ship a gate matching nothing) plus the 2 rejection
  filters. Registered PER KEYWORD so a single dead entry is named rather than averaged
  away: the scan appends on FIRST match, so a dead entry looks exactly like a keyword
  nobody grants. The rejection filters are registered too — a dead one fails silently
  and in the expensive direction, by no longer rejecting.

REGRESSION RISKS:
  - `tags_for` is ADDITIVE — no tag is removed, the signature and return type are
    unchanged. Its four callers (build_pool, tag_synergies main, wishlist, app.py's add)
    all consume a list of strings and are unaffected structurally.
  - `granted_keywords` is a new public function with no prior caller to break.
  - THE REAL RISK IS CENTRALITY, and it is measured rather than assumed: more tags raise
    the dominant theme's count, which raises the 25% centrality floor, which can push
    OTHER themes below it. Deck 35 moved 20 -> 13 central themes this way. No deck's
    tier floor moved, but `cuts` / `similar` / `screen` rankings shift roster-wide — that
    is the intended effect, and it is the reason the rationale sweep fired.
  - Old behaviour correct anywhere? No. "A card that grants deathtouch is not about
    deathtouch" has no defensible reading. The one case worth protecting — a grant to the
    OPPONENT's creatures — is explicitly rejected and pinned by a test.
  - Bounded residual: the grant regex is a phrasing whitelist, so a wording nobody has
    written yet is still missed (G-67's standing shape). Samples were hand-inspected
    across all 12 keywords and were clean; `check_patterns` proves each stays live.
